## 9. 迁移治理方案与后续门槛

当前是“有效结构匹配，执行账本缺失”。不重跑原始 SQL，不手工伪造 ledger，不把定义匹配等同于全部数据回填已验证。本轮未执行 Supabase CLI 的 link/pull/repair/db push，也不新增迁移。

后续由维护者单独批准目标与变更清单后：

1. 备份并验证恢复路径；锁定本报告目标 ref、现有 001–010 文件 SHA-256 和只读目录快照。对数据迁移/种子效果另做获准的最小核对；不导出用户正文或私有 key。
2. 在与目标 PostgreSQL 主版本一致的专用隔离环境重放 001–010，对照 schema-only 基线；审阅 `public`、私有 schema、auth.users 的项目触发器、ACL/RLS 与默认权限，区分平台额外对象，保留差异审核记录。
3. 只有完成该核对后，才提出“仅登记确实已具有效果的历史版本”的管理操作，列出精确版本和回滚账本方案，重新获授权后由维护者执行。不能因本轮 39 函数匹配就自动标记十个版本为已执行。
4. 固定 CLI 版本，显式确认目标；先在专用环境演练账本对齐与下一条迁移的预览，再审批生产。后续只追加新迁移，既有 001–010 与哈希不改，CI 同时检查空库重放和有历史库升级。

`migration repair` 会变更迁移历史；`db pull` 也可能提议记录远端基线，非交互运行会自动接受，不能把它当成无副作用的只读核验命令。参见 [Supabase CLI 工作流](https://supabase.com/docs/guides/local-development/cli-workflows) 与 [repair 官方参考](https://supabase.com/docs/reference/cli/supabase-migration-repair)。这里只给出治理方案，不执行它们。

进入下一阶段仍需：用户完成一题和真实复盘评价，再验证新证据反馈；明确专用项目下补真实双用户、跨实例、过期会话、删除/非空历史与托管旧 revision 冲突；确认平台额外对象与迁移数据效果、账本方案。技术单用户闭环已得到真实证据，**面向真实选手扩大试用/宣布完整 M3.5 或 M4 生产门禁通过仍 BLOCKED**。
